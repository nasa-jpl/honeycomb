★ The End Goal (read this first)

Right now, to build a scene in Honeycomb you list out every model in a JSON config — each URDF, mesh, terrain, etc. — with its position and parent. Your mission is to let someone instead drop in a single USD file that describes the entire scene (all the objects, their hierarchy, their transforms), and have Honeycomb load it all at once.

Then — the fun part — telemetry channels (live/recorded data) should be able to animate the pieces of that USD scene: move the rover, rotate an arm joint, etc.

Why this matters: USD (Universal Scene Description) is becoming the industry standard for describing 3D scenes — Pixar, NVIDIA Omniverse, Apple, and increasingly robotics all use it. Supporting it makes Honeycomb interoperable with a huge ecosystem and way easier to author scenes for.

1 Big Picture: what Honeycomb does with files today

Honeycomb is a 3D robotics visualization tool built on Three.js (the standard WebGL library for the browser). There are three separate "file" jobs happening:

Model files
glTF, OBJ, URDF, STL… → one 3D object each
→
Scene config (JSON)
the list of objects + where they go
→
Telemetry
time-based data that moves objects

Where the code lives

FileWhat it does
pkg/honeycomb/src/Loaders.tsThe loader registry. Every file type registers a loader keyed by extension. A model loader takes a path and returns a Three.js Object3D. This is where a USD loader will plug in.
honeycomb-extensions/src/index.tsWhere all the concrete loaders (glTF, OBJ, URDF…) actually get registered. You'll add your USD one here.
honeycomb-extensions/src/models/The tiny wrapper files for each loader. gltfModelLoader.ts is ~10 lines — a perfect template.
pkg/honeycomb/src/scene.tsDefines the Scene data model — a flat list of objects with parent, position, orientation. This is what a USD file would eventually replace/generate.
honeycomb-extensions/src/drivers/KinematicsDriver.tsThe thing that takes telemetry and moves objects by name. Key insight below.
The single most important thing to understand: telemetry doesn't attach to files — it attaches to objects by name in a map called viewer.objects[name]. So a channel named "rover" moves whatever object is registered as "rover". Everything in this project revolves around getting USD prims (nodes) into that map with the right names.

2 Concepts Primer (the new stuff, quickly)

USD in plain English

USD (Universal Scene Description) is a format and a runtime for describing 3D scenes. Unlike glTF (which delivers one asset), USD is built to assemble whole scenes from many pieces without destroying the originals.

  • Stage — the fully composed scene you actually view.
  • Prim — a node in the scene tree (an Xform/transform, a Mesh, a Camera, a Light). Each has a path like /rover/arm/wrist.
  • Attribute — typed data on a prim (position, color…), and it can be time-sampled (change over time — sound familiar? that overlaps with telemetry).
  • Composition — USD's superpower: references, payloads, and variants let many files layer into one scene.
  • File types — .usda (human-readable text), .usdc (binary), .usdz (zipped bundle with textures — most web-friendly), .usd (either).
Reality check — and good news (updated Aug 2026): This repo currently installs three@0.169.0, which ships only the old USDZLoader — it reads a subset of ASCII .usda/.usdz geometry and explicitly throws on binary .usdc ("crate") files. But as of three r183+ there's a new, separate USDLoader that genuinely decodes binary .usdc — in pure JavaScript, no WebAssembly required (it hand-rolls the crate parser). So the old "you'll eventually need OpenUSD-in-WASM for .usdc" plan is no longer necessary for basic geometry. The one catch: getting USDLoader means upgrading three from 0.169 → ≥0.183 across the workspace (details in Week 2). Plan: prove the plumbing on the installed ASCII loader first, then upgrade and switch to USDLoader.

Three.js in plain English

Everything visible is an Object3D arranged in a tree. Meshes have geometry + material. Objects have .position and .quaternion (rotation). Moving something = changing those values. Honeycomb already does all the rendering — you mostly produce Object3Ds and give them the right names.

Two paths: Grafana vs Caspian (important nuance)

There are two front-ends, and they wire telemetry to objects a little differently — but both end up at the same runtime (KinematicsDriver → viewer.objects).

PathHow channels get matched to objects
Grafana (recommended)There's a real editor UI. Every object's position, orientation, and each joint is a Channel you bind to a data field via a dropdown (editors/ObjectEditor/TransformEditor.tsx → editors/ChannelEditor.tsx). At playback, GrafanaKinematicsAnimator builds one AnimatedRobot per object (keyed by obj.id) and emits state → same driver.
Caspian (legacy)Bindings come from the JSON config directly; objects are looked up by name in viewer.objects[name]. No editor UI.
Why this matters for USD (and it's great news): the Grafana channel-matching UI is generated entirely from options.scene — the list of SceneObjects. So the moment your USD prims become SceneObjects (each with a stable id, name, position, orientation, joints), they automatically show up in the editor and become bindable to telemetry channels — no new UI needed. This makes "USD → SceneObjects" (milestone M4) the real unlock.

Two loaders: USDZLoader (installed) vs USDLoader (upgrade)

There's a second either/or on top of Grafana-vs-Caspian: which three.js loader you build against. This was verified against the actual code (Aug 2026):

LoaderWhat it does & when to use it
USDZLoader
(in repo now, three 0.169)		Parses ASCII .usda and ASCII-inside-.usdz only. It detects binary .usdc and throws ("Crate files… are not supported"). Use it for Weeks 1–3 — zero dependency changes, so you can prove the whole pipeline fast.
USDLoader
(three r183+ / ≥0.183)		The new superset loader. Genuinely decodes binary .usdc (crate format) in pure JS — no WASM. USDZLoader is now a deprecated subclass of it. Switch to it once you upgrade three (see Week 4 / the upgrade note).
Recommended sequence: don't block on the upgrade. Build your loader wrapper against the ASCII path first and hit M0–M2. Then do the three 0.169 → ≥0.183 bump as its own separate branch/PR, and finally swap in USDLoader to unlock .usdc. Keeping the dependency bump off the critical path means a rendering regression can't sink your USD milestones.

⟳ Dev loop: how do I test a change?

Great instinct to ask — this trips people up. The key fact about this repo: the pkg/* packages are consumed as raw TypeScript source, not pre-built dist/ folders. I checked — pkg/honeycomb/package.json has "main": "src/index.ts", there's no build step, and it's a Yarn workspace so node_modules/@gov.nasa.jpl.honeycomb/* symlinks straight into pkg/*. The app's own webpack compiles that source.

What this means (the good news): when you edit a core file like usdModelLoader.ts in pkg/honeycomb-extensions/, you do NOT separately build the package. The app's webpack (running in --watch) sees the changed source through the symlink and rebuilds automatically. There is no "rebuild the honeycomb package" step.

Grafana (recommended) — the two-process loop

Grafana loads the plugin from app/grafana/dist/, and the docker-compose.yaml bind-mounts ./dist into the container. So the loop is:

Terminal / actionCommandWhat it does
1. Build in watch modecd app/grafana && yarn devWebpack watches app AND pkg/* source, rebuilds dist/ on every save (incl. your core-file edits).
2. Run Grafana + InfluxDBdocker compose up (or yarn server)Serves the plugin from the mounted dist/ at localhost:3001.
3. See your changeReload the browser tabAfter webpack finishes a rebuild, a refresh loads the new bundle. No container restart needed.
When you DO need more than a browser refresh:
  • Restart yarn dev — after changing a package.json (new dep) or the webpack config. Watch mode doesn't pick those up.
  • docker compose up --build — after changing anything under .config/ (the dockerfile, provisioning) or if the plugin isn't showing up at all.
  • yarn install at the repo root — after pulling changes that touch dependencies, so the workspace symlinks are correct.

Caspian (legacy) — the one-process loop

Simpler, no Docker: cd app/caspian && yarn start runs webpack serve (dev server with hot reload) at localhost:9000. Edit a core file, webpack recompiles, the page reloads. Good for a fast "does my loader return an Object3D?" check before you deal with Grafana's telemetry-binding UI.

Fastest inner loop of all: unit tests

You don't need a running app to test loader logic. Packages use Jest (pkg/honeycomb/package.json → "test": "jest"; there's a pkg/honeycomb/test/ dir). Run yarn jest in the package (or npx lerna run test from root) for a sub-second loop while you get parsing/naming right — then verify visually in the app. This is also your Week 4 "add a couple of tests" deliverable.

Recommended rhythm: Jest for loader/mapper logic → Caspian for a quick visual "it renders" → Grafana for the real telemetry-binding demo (M2+). Keep yarn dev running the whole time; you'll mostly just be hitting browser-refresh.

4 Staying adaptable (important!)

This plan will change as you learn — that's expected and good. A few principles to keep it flexible:

  • Milestones > weeks. The M0–M4 milestones are the real backbone. This is a compressed 4-week pace, so if a week slips, slide the milestone — don't panic. Getting M0→M2 solid beats a rushed, shaky M4.
  • Depth-first when stuck. If the limited ASCII loader blocks you, don't rabbit-hole — note it, drop to a simpler test asset, keep the pipeline moving. (The binary .usdc answer is the three upgrade, and that's deliberately parked at the end.)
  • Write findings down immediately (Notes box below). Future-you and your mentor will thank you.
  • Re-scope weekly. Every Friday, glance at this page: what moved, what's blocked, what's next. Edit tasks freely — it's your file.
  • Ask early. A 10-min question to a maintainer beats 2 days stuck. Especially on coordinate frames and the driver binding.
